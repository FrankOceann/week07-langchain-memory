# 安全文件处理 Agent：长文本检索测试资料

这是一份专门用于测试知识库 RAG 的长文本资料。它的目标不是提供唯一正确的生产方案，而是让同一个文件中包含多个相隔较远的话题，以便观察系统是否能把文档切分为多个片段，并在提问时找到真正相关的片段。阅读本资料时，应区分三件事：模型可以提出行动建议，工具负责实际执行，执行程序负责在边界处做确定性的校验。模型的语言能力很强，但模型输出不能直接等同于系统权限。一个安全的 Agent 应当把“建议做什么”和“是否允许做”拆开处理。

## 第一部分：工具权限与用户确认

任何工具都应该先定义明确的能力范围。一个读取工具只负责读取被允许的文本；一个保存工具只负责将用户确认的内容写入预先约定的位置；一个网络工具只负责访问已经允许的服务。工具名称、参数和权限不应由模型临时发明，而应由 Python 程序中的注册表固定下来。这样做的意义是，模型即使给出了不合理的工具名或参数，执行层也可以拒绝它。最小权限原则要求工具只拿到完成当前任务所必需的最少能力。例如，一个总结文本的工具不需要删除文件权限，一个查询知识库的工具不需要访问整个电脑的权限。

对可能产生副作用的操作，系统应当要求用户在执行前进行确认。副作用包括写入、删除、修改、发送外部请求，或将数据提交给第三方服务。确认提示应清楚说明“将做什么、影响什么、是否可以取消”，而不是只问一个模糊的“确定吗”。用户输入“确认”后，程序才执行保存或修改；用户输入“取消”后，程序必须清除待执行状态。确认机制不能只靠模型的一句承诺，因为模型可能误解上下文或受到不可信输入影响。真正的防线是：工具执行前的本地代码检查待确认状态和用户的明确选择。

权限控制也需要可观察性。每次工具调用至少应记录工具名称、是否需要确认、输入是否通过校验、执行成功或失败的结果。日志中不应保存 API Key、密码、完整隐私文本等敏感信息。若某个请求被拒绝，日志应说明拒绝的原因，例如“参数格式不正确”“工具未注册”“路径不在允许目录内”或“等待用户确认”。这些记录有助于定位问题，也能让开发者验证权限规则确实被执行，而不是只写在提示词里。

## 第二部分：受限文件访问与路径安全

文件工具必须有允许访问的根目录，例如项目中的 data 目录。用户给出的文件名不是可靠路径，程序需要先把它与允许目录组合，再调用 Path.resolve() 得到规范化后的绝对路径。随后必须检查该路径仍位于允许目录之内。若请求包含 ../、盘符、绝对路径、符号链接或其他试图跳出根目录的写法，校验结果应当拒绝，而不是尝试“猜测用户真正想访问什么”。路径校验的目标不是让程序更方便地找到文件，而是防止路径穿越导致任意文件被读取。

一个稳妥的读取流程可分为四步。第一步，限制候选文件类型，例如只允许直接位于 data 目录的 UTF-8 .txt 文件，不递归扫描未知子目录。第二步，验证文件名和解析后的路径；找不到文件时返回清晰的“不存在”说明。第三步，在受控范围内读取文本并处理编码错误；不能因为一个文件损坏就泄露堆栈、环境变量或其他内部细节。第四步，把读取结果连同来源文件名交给后续工具，使最终回答可以追溯到原始资料。来源标识是可解释性的基础，例如 filename.txt#chunk-1 表示回答使用了该文件的第二个片段。

文件安全并不等于拒绝所有请求。正确目标是允许合理的、被授权的读取，同时稳定拒绝越权读取。测试时应分别覆盖正常文件、空文件、不存在文件、空文件名、包含 ../ 的文件名和绝对路径。自动化测试可用临时目录构造这些情形，避免影响真实 data 目录。路径规则一旦被测试固定下来，之后即使重构工具实现，也可以防止无意中放宽安全边界。

## 第三部分：检索、日志与故障处理

知识库 RAG 的流程通常从文档切分开始。长文档不会整体直接送给模型，而是被切成带重叠的 Chunk。每个 Chunk 需要保存来源文件、从零开始的片段编号和原文文本。重叠部分能减少一句话刚好被切在边界上时的信息丢失，但 Chunk 过大可能使召回不够精确，Chunk 过小则会丢失上下文。因此 Chunk 大小、重叠长度和 Top-K 数量都是可测试、可调整的参数，而不是模型自动解决的问题。

Embedding 服务把文本转换为向量，检索时用问题向量与文档向量计算相似度，并取分数最高的少量片段。高分不等于事实正确，只表示文本在向量空间中更接近问题。最终回答必须保留检索到的来源，不能把不存在的文件名、片段编号或引用内容编造出来。如果检索结果不支持问题，应明确说明“资料不足”或“知识库没有相关资料”，而不是补充外部常识后假装来自本地文档。对“提示注入防护”等资料没有直接覆盖的主题，也应把根据资料做出的间接推论与资料原文区分开。

外部服务可能超时、限流、网络不可用或返回格式异常。系统应在调用 Embedding 服务和聊天模型时捕获异常，向用户给出简洁、可行动的错误信息，例如“模型服务暂时失败，请稍后重试”。日志可以记录错误类别、请求阶段和是否可重试，但不能记录密钥。对于一次用户请求，还应设置工具调用次数上限，避免模型反复调用同一种工具消耗成本。若模型返回非结构化的伪工具调用文本，执行程序应拒绝将其当作真实命令执行。

## 第四部分：长文本测试结论

本资料包含四个主题：工具权限、路径安全、RAG 检索以及错误处理。它们被刻意放在不同段落中。测试人员可以提问“为什么副作用操作需要确认”“如何阻止路径穿越”“Chunk 重叠有什么作用”“服务超时时系统应如何处理”。理想结果是，系统主要返回对应主题附近的 Chunk，并在答案中给出 rag_long_test.txt#chunk-N 形式的来源。若一个问题要求综合多个主题，回答可以引用多个片段；若问题与本资料无关，例如实时天气或未提供的业务数据，回答应明确资料不足。通过这些案例，可以检查长文档切分、Top-K 排序、来源引用、资料不足声明和工具安全边界是否共同正常工作。
